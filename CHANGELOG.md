# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- API vote/stake/gossip dashboard queries no longer recompute cheap, slow-moving scalars on every request against expensive window-function views (the largest remaining CPU block on the shared ClickHouse cluster, ~15%). The network total stake (`sum(activated_stake_lamports)`, previously a CTE copy-pasted across seven timeline query sites) and the current cluster slot (`max(cluster_slot)`, two per-request subqueries in the multicast members handler) are now served from a per-env, short-TTL in-memory cache (5-min for total stake, 15s for slot; concurrent misses collapse via singleflight). The default validators listing (first page, stake desc, no filters) — polled continuously by the UI and an external consumer — gets page-cache coverage refreshed every ~60s, so the same fixed answer is no longer recomputed ~6,500×/day. Behavior-preserving: no API response shape changes; the `X-Cache` header on the validators listing is additive (#732)
- Indexer link-latency previous-RTT lookups no longer scan each circuit's full history on every append (the top lake-owned CPU consumer, ~9% of the shared ClickHouse cluster): the last non-zero RTT per circuit is carried forward in memory, so steady-state appends compute IPDV with no ClickHouse read at all. Cache misses (restart, new circuit) are seeded by a 2-day-bounded scan, with an unbounded fallback restricted to just the circuits the bounded pass missed, so quiet circuits keep their carried-forward IPDV baseline. The companion `max(sample_index)` queries get a 4-day `event_ts` bound for partition pruning, backstopped by an in-memory carry-forward of every max index the process has written or read back — so a circuit-epoch that outlives the bound while still being fetched (an agent quiet for days, or an epoch running longer than 4 days) is refetched and re-inserted at most once per process start, not on every refresh. Backfill IPDV baselines now carry forward across epochs within a run instead of re-reading latest-overall per epoch. Adds `doublezero_data_indexer_clickhouse_prev_rtt_query_total{dz_env,table,kind}` and `doublezero_data_indexer_clickhouse_prev_rtt_fallback_circuits_total{dz_env,table}` to verify cache behavior (#720)
- Indexer telemetry-usage baseline query no longer re-scans ClickHouse on nearly every refresh: the in-memory baseline cache is now validated against the data watermark it represents instead of a wall-clock TTL, so steady-state refreshes reuse it and the `argMaxIf` scan runs only on startup/backfill. A cache hit is additionally gated on ClickHouse's max `event_ts`: if another writer (e.g. the admin backfill's continue mode) advanced it past the watermark, the cache is discarded and re-scanned instead of serving stale baselines. A failed already-written dedup query now fails the refresh instead of re-emitting overlap rows against cached end-of-window baselines. The raw lookback is cut 7d→2d, and backfill carries baselines across contiguous chunks, including zero-row chunks (fixes the June-backfill 60s-timeout mode). Adds `doublezero_data_indexer_clickhouse_baseline_query_total{dz_env}` to track cache misses (#702)
- Non-actionable failures no longer log at ERROR (which pages on-call): indexer view refreshes and ingest workflows escalate WARN→ERROR only on sustained consecutive failures; slack, agent, and worker log sites classify transient and client-caused errors as WARN; probe-write, optional-listener, and shutdown-cleanup failures demote to WARN (#696)
- `dberror` moved from `api/handlers/dberror` to `utils/pkg/dberror` so all services can share transient-error classification (#696)

### Fixed

- Indexer telemetry-usage ingest no longer silently drops data when the watermark falls more than `QueryWindow` (1h) behind: the refresh now catches up from the watermark using the existing capped-chunk pacing instead of jumping to `now−1h` and discarding the intervening span (staging was losing ~30% of mainnet-beta interface-counter rows this way; a >1h prod ingest outage would have lost the whole outage span). The only remaining skip-ahead is an explicit 24h horizon that logs the exact dropped span at ERROR — once per distinct stall, WARN on repeats — so a human sees it and can backfill. Catch-up convergence is now observable before the horizon: the refresh reports the real max ingested `event_ts` as `SourceMaxEventTS` (ingestion-log freshness shows true watermark lag instead of wall-clock now) and WARNs when lag fails to decrease across consecutive capped cycles (a cycle time at or above the 10m capped span means lag grows instead of closing). A capped catch-up span that stays empty at the source for the full 1h late-arrival window now advances the catch-up anchor past it, so a genuine source data gap traverses at the paced rate (trailing `now−1h`) instead of pinning ingest (previously the 1h jump was the only escape), while a source stall that later replays buffered data within the window still loses nothing (#718)
- Shred subscribers dashboard now reflects per-escrow activation: seat status, balance, and prepaid epochs derive from the greatest single escrow (`max`), not the sum across escrows (`sum`), matching how the oracle evaluates activation and renewal. A seat with two escrows of $5.83 + $25.65 at a $30/epoch price now correctly shows as inactive/expired (spendable $25.65, 0 prepaid) instead of pending. Internal handlers rename `total_usdc_balance` to `spendable_usdc_balance` and add `all_escrows_usdc_balance` (the across-escrow total, so operators can still see stranded funds). The public `/api/v1/edge/shreds/*` responses add both new fields and keep `total_usdc_balance` as a deprecated alias of the across-escrow sum, so the change is backward compatible. The seat table's Prepaid column now sorts by prepaid epochs (spendable / price) rather than the stale per-epoch price, and the `prepaid:` filter is now honored (#715)
- Indexer interface-counter data (`fact_dz_device_interface_counters`) is no longer permanently ~1h stale: the telemetry-usage catch-up cap is now anchored at `maxTime` (the ingest watermark) instead of `queryStart`, which had made the cap equal the 5m re-read overlap so an incremental refresh could never query past `maxTime` — every cycle re-read only rows that dedup out and inserted nothing, and `max(event_ts)` sawtoothed ~1h behind `now()`. Steady state now ingests the overlap plus one chunk (~10m, 2 Flux queries) and advances every refresh. `RefreshTelemetryUsage` gets a dedicated 10m activity `StartToCloseTimeout` (was the shared 5m) to bound the two-query worst case plus ClickHouse work, preventing the #665/#671 timeout loop. The post-downtime catch-up memory bound is unchanged (#708)

### Added

- Publish serviceability feeds (Generalized Payments) to ClickHouse: new `dz_feeds_current` view (SKU catalog: feed → metro + joinable multicast groups), plus `dz_users_current.feed_pks` (JSON array of the EdgeSeat feeds a connected user consumed seats on) and `dz_access_passes_current.feed_seats` (per-feed seat billing lifecycle on EdgeSeat passes). Bumps the doublezero SDK to pick up the `Feed` account, `User.FeedPks`, and `AccessPass.FeedSeats` (#2068)
- Shared `utils/pkg/logger` helpers: transient-aware `logger.Error`/`logger.Warn` and consecutive-failure `logger.Escalator`; logging-level convention documented in CLAUDE.md (#696)
