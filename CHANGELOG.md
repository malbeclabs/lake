# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- The page cache's most expensive entries now refresh on a per-entry cadence instead of every cycle: Network Health's historical groups and the metro-pair latency comparison every 30 minutes, the Network Health overview and the two 24h edge-scoreboard aggregates every 5 minutes. Those three groups measured 14.34% of production ClickHouse CPU over a 2.1-hour span while their inputs move on day or 24h-window timescales. Point-in-time views are unchanged; the edge-scoreboard live tail needed a cursor-coverage guard so a cadenced seed cannot skip slots. `cacheEntry.everyN` (a cycle count) becomes `cacheEntry.every`, a wall-clock duration, and `logger.Escalator` gains an opt-in `ErrorAfterDuration` so a degraded Network Health panel still pages on time under a long cadence (#777)
- Finishes the #732 vote/stake/gossip cache work, reclaiming the ~7% of shared-ClickHouse CPU that #736 left behind. Two gaps: the `total_stake` CTE still ran per-request outside `timeline.go` (the validators listing, validator detail, and DZ user detail handlers), and the validators page cache was gated on `limit=100` while 100% of measured production traffic to `/api/solana/validators` uses `limit=900` and so bypassed it on every call. The three surviving CTE copies now read a per-env 5-minute cached scalar (a separate value from #736's, since these sites filter on `epoch_vote_account` — reusing the unfiltered total would have shrunk every `stake_share`), and the page cache now holds the complete unfiltered stake-desc set with the handler slicing whatever page a client requests, so cache eligibility no longer depends on the client's page size. Cached responses carry `Cache-Control: public, max-age=60` so pollers self-throttle to the refresh cadence, and every response carries `Vary: X-DZ-Env` since the env arrives as a header and isn't part of the URL. The cache read is bounded by its own deadline rather than the caller's, so a Postgres slowdown degrades to the live query instead of stalling the endpoint. A cached entry that can't answer the request — row cap exceeded, empty because a refresh caught the view mid-reload, or old enough that the refresh worker must have stopped running entirely — falls through to the live query rather than serve a truncated, empty, or indefinitely frozen page. The page-cache key moves from `validators` to `validators:all` so a rolling deploy can't have old pods serve the new complete-set payload verbatim. Behavior-preserving: no API response shape changes (#743)
- API vote/stake/gossip dashboard queries no longer recompute cheap, slow-moving scalars on every request against expensive window-function views (the largest remaining CPU block on the shared ClickHouse cluster, ~15%). The network total stake (`sum(activated_stake_lamports)`, previously a CTE copy-pasted across seven timeline query sites) and the current cluster slot (`max(cluster_slot)`, two per-request subqueries in the multicast members handler) are now served from a per-env, short-TTL in-memory cache (5-min for total stake, 15s for slot; concurrent misses collapse via singleflight). The default validators listing (first page, stake desc, no filters) — polled continuously by the UI and an external consumer — gets page-cache coverage refreshed every ~60s, so the same fixed answer is no longer recomputed ~6,500×/day. Behavior-preserving: no API response shape changes; the `X-Cache` header on the validators listing is additive (#732)
- Indexer link-latency previous-RTT lookups no longer scan each circuit's full history on every append (the top lake-owned CPU consumer, ~9% of the shared ClickHouse cluster): the last non-zero RTT per circuit is carried forward in memory, so steady-state appends compute IPDV with no ClickHouse read at all. Cache misses (restart, new circuit) are seeded by a 2-day-bounded scan, with an unbounded fallback restricted to just the circuits the bounded pass missed, so quiet circuits keep their carried-forward IPDV baseline. The companion `max(sample_index)` queries get a 4-day `event_ts` bound for partition pruning, backstopped by an in-memory carry-forward of every max index the process has written or read back — so a circuit-epoch that outlives the bound while still being fetched (an agent quiet for days, or an epoch running longer than 4 days) is refetched and re-inserted at most once per process start, not on every refresh. Backfill IPDV baselines now carry forward across epochs within a run instead of re-reading latest-overall per epoch. Adds `doublezero_data_indexer_clickhouse_prev_rtt_query_total{dz_env,table,kind}` and `doublezero_data_indexer_clickhouse_prev_rtt_fallback_circuits_total{dz_env,table}` to verify cache behavior (#720)
- Indexer telemetry-usage baseline query no longer re-scans ClickHouse on nearly every refresh: the in-memory baseline cache is now validated against the data watermark it represents instead of a wall-clock TTL, so steady-state refreshes reuse it and the `argMaxIf` scan runs only on startup/backfill. A cache hit is additionally gated on ClickHouse's max `event_ts`: if another writer (e.g. the admin backfill's continue mode) advanced it past the watermark, the cache is discarded and re-scanned instead of serving stale baselines. A failed already-written dedup query now fails the refresh instead of re-emitting overlap rows against cached end-of-window baselines. The raw lookback is cut 7d→2d, and backfill carries baselines across contiguous chunks, including zero-row chunks (fixes the June-backfill 60s-timeout mode). Adds `doublezero_data_indexer_clickhouse_baseline_query_total{dz_env}` to track cache misses (#702)
- Non-actionable failures no longer log at ERROR (which pages on-call): indexer view refreshes and ingest workflows escalate WARN→ERROR only on sustained consecutive failures; slack, agent, and worker log sites classify transient and client-caused errors as WARN; probe-write, optional-listener, and shutdown-cleanup failures demote to WARN (#696)
- `dberror` moved from `api/handlers/dberror` to `utils/pkg/dberror` so all services can share transient-error classification (#696)

### Fixed

- Maps no longer render an "API KEY REQUIRED" watermark across every tile. CARTO began requiring a key on the basemap endpoints and answers a keyless request with HTTP 200 and a valid PNG carrying the text burned into it, so MapLibre saw a good tile and nothing errored or logged. Tile URLs now carry a `CARTO_API_KEY` served to the browser through `/api/config` — the key is public by construction, and CARTO has no domain restriction for basemap keys, so it is disclosed rather than scoped — bounded by their fair-use quota and their right to revoke. The URL, duplicated verbatim in three map components, moves to `web/src/lib/basemap.ts`, which is also where the CSP allowlist in `api/main.go` now points: a provider or host change that skips the CSP is the same class of silent failure (#804)

- A deploy no longer leaves the DZ ingest, Solana ingest, or rollup workflows replaying the previous deploy's history: all three had the same non-atomic terminate-and-start as the page cache (#776), where a failed or raced `TerminateWorkflow` let `ExecuteWorkflow` return a handle on the still-running run with no error, and the workflow then panicked on nondeterminism against the new worker code and stopped ingesting. Each start is now a single server-side atomic call, and each `workflow started` line names the run it started. Terminating one of these workflows by hand no longer wedges its watcher in a hot reattach loop either: with no replacement run started, the watcher re-fetched the same closed run, whose `Get` returns at once, so it spun at RPC speed logging a WARN per iteration for the life of the process (#778)
- Epoch ETAs on the Solana Overview and DoubleZero Ledger pages are now measured from each chain's own slot rate rather than assuming a fixed 0.4s, which was wrong on both chains and drifting further as Solana steps down through the SIMD-0525 stages. The DoubleZero ledger runs ahead of its nominal target, so both of its epoch figures drop ~8% on deploy (#2318)
- A deploy no longer leaves the page cache with no refreshes by adopting the previous deploy's workflow run instead of restarting it. Staging spent ~6 hours in that state, running the expensive queries behind every cached page on every request. The restart is now atomic, and the start log line names the run it started (#776)
- Devices and links that stop reporting telemetry now surface. The `no_data` incident type had never fired for any entity: both incident views find missing rollup buckets with a LEFT JOIN and then test `WHERE a.bucket_ts IS NULL`, but ClickHouse runs with `join_use_nulls = 0`, so an unmatched row carries `1970-01-01` and the test never matched. They now compare against the zero date, and drop gaps shorter than 3 buckets so a single-bucket ingestion blip does not raise an incident on all 99 devices at once. The device status grid marked a square red only when the square held no row at all, so a 20-minute outage that straddles a 20-minute square boundary left a row on each side and rendered healthy. Each square now reports its missing 5-minute source buckets as `missing_sub_buckets`, and 2 or more marks it degraded with a `partial_data` reason. This is what hid the 2026-08-12 TeraSwitch outage, where all 13 devices went dark from 03:50 to 04:10 UTC with a green status page (#771)
- Applying any filter on the incidents page no longer 500s. The shared link and device filter-clause builders emitted JOIN-alias-qualified columns (`cc.code`, `l.code`, `ma.code`, …) into every caller, including the default-threshold query path that reads the flattened `link_incidents_v` / `device_incidents_v` views and has no JOINs at all — so ClickHouse rejected the query with `Unknown expression or function identifier`. Each builder now takes the column names valid in its caller's scope, so the two paths cannot drift again. Device-filtered link requests fall back to the JOIN-based query, since the link view exposes no device codes; that fallback runs with the view's 8-day lookback and 5-minute buckets, so applying a device filter cannot change which incidents exist or how their peaks aggregate (#763)
- The device and link multicast-delivery endpoints no longer scan the same expensive view twice per paged section: each page query now carries its own total as a window aggregate (`count() OVER ()`, and `countIf(...) OVER ()` per health-status bucket), removing five full scans of `enriched_ip_mroute`/`enriched_ip_mroute_oifs`/the health tables per request and taking every fan-out branch to exactly one query deep. Totals are unchanged, including the `unknown` health bucket, which stays the remainder so an unrecognized `health_status` still lands there. A page whose offset lands past the end of the result set has no row to carry the total, so it alone falls back to the count query and the pager keeps reporting the true total. Each query's `max_execution_time` also drops 30s→20s, and is capped at whatever is left of the request deadline when that is less — ClickHouse counts the cap from when a query starts executing, so a query that queued on the fan-out semaphore or runs second in its branch would otherwise get a full fresh budget, below the handler's own 30s request deadline, so an overrun now surfaces as a ClickHouse `TIMEOUT_EXCEEDED` naming the query instead of a `context.DeadlineExceeded` the request path classified as a client disconnect and dropped — a 500 with no log line at all. That classification is fixed generally across `api/handlers`' three log helpers (`logError`, `logWarn`, `internalError`): a context deadline on a request path is the handler's own budget expiring (net/http never sets one on `r.Context()`), so it now logs at WARN instead of being silently discarded. This also restores the missing line on handlers whose only bound is their own budget, e.g. `GetMulticastGroupMembers` and the swap-rate served-stale fallback. `logger.Warn`, whose only production caller was the old `logWarn` and which dropped on `IsClientDisconnect` as a whole, is removed so a request path cannot re-adopt the pattern. (#748)
- A user gaining or losing an EdgeSeat feed seat no longer renders as a contentless "updated (0 fields)" timeline event: the users section of `entity_changes_v` now enumerates `feed_pks` in `changed_fields`. `feed_pks` was already part of the users `attrs_hash` (#2068), so the SCD delta fired but named no field. Same shape as the earlier `bgp_status` follow-up, and retroactive — the view is computed at query time. The user timeline details fetcher now also diffs `bgp_status` and `feed_pks`, so neither disappears from an event's title and field chips when it changes together with an already-diffed field (#2092)
- Indexer telemetry-usage catch-up can no longer livelock on an identical window. A capped catch-up cycle that failed after its window was computed re-queried exactly the same window on the next cycle — forever, since `max(event_ts)` only advances on a successful insert and nothing about the window depended on the previous outcome — which froze the staging watermark at `2026-07-28T18:11:36Z` for ~22.6h across 76 cycles, ingesting nothing until the 24h horizon skip dropped the span. The catch-up span is now adaptive (AIMD): two capped cycles failing back-to-back halve it (floor 1m, ~2.5× less work per cycle by the floor), and each successful capped cycle adds 1m back up to the previous fixed cap, so work that a cycle cannot afford is always retried more cheaply. The trigger is the failure streak rather than any single failure, because a success moves the watermark: halving on every failure would tie the steady-state span to the failure rate, so a sustained ~50% rate uncorrelated with window size (InfluxDB rate limiting) would walk the span to the floor and make catch-up diverge where the old fixed span converged. Steady-state (uncapped) cycles never touch the span, so a healthy environment behaves exactly as before. Adds `doublezero_data_indexer_telemetry_usage_watermark_timestamp_seconds{dz_env}`, published at the top of every refresh including failing ones, so a frozen watermark is visible from the first failing cycle instead of ~24h later — an absolute timestamp rather than a pre-computed lag, since `time() - <gauge>` keeps climbing even if refreshes stop running entirely. Each shrink logs WARN, and the `capping catch-up window` line escalates to WARN with a `sameWindowCycles` count once the window repeats *and* the span is pinned at the floor (a repeating window with the span at its ceiling is an already-bounded source stall, not a stuck catch-up). `dztelemusage.WorstCaseRefreshFluxBudget` names the worst-case InfluxDB cost of one capped refresh and a dzingest test asserts the activity's `StartToCloseTimeout` exceeds it — the relationship that #711 and #714 set independently and silently broke (#740)
- Indexer `SyncMSDP` (and the identically-shaped mroute/ISIS S3 sources) no longer page on transient S3 failures: `dberror.Classify` now recognizes the AWS SDK v2 "https response error StatusCode: 200" (S3's documented 200-with-embedded-error blip) and retryable 5xx (500/502/503/504) shapes as transient connectivity, so the ingest escalator holds them at WARN until sustained (≥10 consecutive iterations). Actionable 4xx (403/404) and permanent 501/505 still page (#731)
- Indexer DZ ingest workflow no longer emits a second ERROR line duplicating the activity-side escalation-gated page: every activity failure that reached the workflow future — StartToClose timeouts and panics; ordinary failures never do, since `activities.refresh` swallows them — produced both the activity-level escalated ERROR and a workflow-level duplicate, doubling every timeout-driven page on `#alerts`/`#alerts-l2` (a #697 regression via #711's `MaximumAttempts: 1`, which made every `RefreshTelemetryUsage` deadline miss surface immediately). Workflow-level activity-failure lines are now WARN-only; the activity layer's consecutive-failure escalation owns the paging decision. Any dashboard or alert keyed on the workflow `"<name> refresh failed"` / `"<name> sync failed"` lines at `level="ERR"` must instead key on the activity-side `"activity refresh failed"` line, which carries `activity=<name>` and `consecutive_failures` (#730)
- The device multicast-delivery endpoint (`/api/dz/devices/{pk}/multicast-delivery`) runs its independent ClickHouse queries concurrently in two dependency stages instead of ~11 sequentially, cutting request wall time to roughly the slowest single query. This removes the CI timing flake where `TestDeviceMulticastDelivery_*` intermittently hit the 30s request deadline on loaded runners, and improves production latency. Responses, error precedence, and source-unavailable fallbacks are unchanged (#735)
- Indexer telemetry-usage ingest no longer silently drops data when the watermark falls more than `QueryWindow` (1h) behind: the refresh now catches up from the watermark using the existing capped-chunk pacing instead of jumping to `now−1h` and discarding the intervening span (staging was losing ~30% of mainnet-beta interface-counter rows this way; a >1h prod ingest outage would have lost the whole outage span). The only remaining skip-ahead is an explicit 24h horizon that logs the exact dropped span at ERROR — once per distinct stall, WARN on repeats — so a human sees it and can backfill. Catch-up convergence is now observable before the horizon: the refresh reports the real max ingested `event_ts` as `SourceMaxEventTS` (ingestion-log freshness shows true watermark lag instead of wall-clock now) and WARNs when lag fails to decrease across consecutive capped cycles (a cycle time at or above the 10m capped span means lag grows instead of closing). A capped catch-up span that stays empty at the source for the full 1h late-arrival window now advances the catch-up anchor past it, so a genuine source data gap traverses at the paced rate (trailing `now−1h`) instead of pinning ingest (previously the 1h jump was the only escape), while a source stall that later replays buffered data within the window still loses nothing (#718)
- Shred subscribers dashboard now reflects per-escrow activation: seat status, balance, and prepaid epochs derive from the greatest single escrow (`max`), not the sum across escrows (`sum`), matching how the oracle evaluates activation and renewal. A seat with two escrows of $5.83 + $25.65 at a $30/epoch price now correctly shows as inactive/expired (spendable $25.65, 0 prepaid) instead of pending. Internal handlers rename `total_usdc_balance` to `spendable_usdc_balance` and add `all_escrows_usdc_balance` (the across-escrow total, so operators can still see stranded funds). The public `/api/v1/edge/shreds/*` responses add both new fields and keep `total_usdc_balance` as a deprecated alias of the across-escrow sum, so the change is backward compatible. The seat table's Prepaid column now sorts by prepaid epochs (spendable / price) rather than the stale per-epoch price, and the `prepaid:` filter is now honored (#715)
- Indexer interface-counter data (`fact_dz_device_interface_counters`) is no longer permanently ~1h stale: the telemetry-usage catch-up cap is now anchored at `maxTime` (the ingest watermark) instead of `queryStart`, which had made the cap equal the 5m re-read overlap so an incremental refresh could never query past `maxTime` — every cycle re-read only rows that dedup out and inserted nothing, and `max(event_ts)` sawtoothed ~1h behind `now()`. Steady state now ingests the overlap plus one chunk (~10m, 2 Flux queries) and advances every refresh. `RefreshTelemetryUsage` gets a dedicated 10m activity `StartToCloseTimeout` (was the shared 5m) to bound the two-query worst case plus ClickHouse work, preventing the #665/#671 timeout loop. The post-downtime catch-up memory bound is unchanged (#708)

### Added

- The geolocation explorer page gains a **DZDP Concentration** view: hero stats, an anchor-point map, a country bar chart, an ASN concentration list, and a CTA banner over the DZDP geolocation data. The two endpoints behind it, `/api/geo/concentration` and `/api/geo/validators`, already existed but had no caller until now; nearest-metro assignment moves out of a ClickHouse cross join into Go (#PRNUM)
- A view switcher (QA Explorer / DZDP Concentration / DZDP Validators) on the geolocation explorer, with the selection synced to a `view` URL query param so a view is linkable (#PRNUM)
- Serviceability Feed accounts are now first-class timeline entities: `entity_changes_v` gains a `feed` section over `dim_dz_feeds_history`, the timeline API gains a feed details fetcher (old→new field diffs, feed entity card with a metro link, `metro:` search matching), and the timeline UI gains a Feeds filter chip (on by default). `changed_fields` covers every column in the feed `attrs_hash` (`code`, `name`, `owner_pubkey`, `metro`, `groups`), so no feed update can render as "0 fields". Retroactive: all feed history since #2068 started ingesting surfaces at once (#2092)
- Publish the shred-subscription retransmit-only metro flag to ClickHouse: new `dim_dz_shred_metro_histories_current.retransmit_only_enabled` (bit 0 of the on-chain `MetroHistory.flags` — when set, every device in the metro serves the retransmit multicast group only, leader group excluded). Exposed on the internal `/api/dz/shreds/devices` response (inherited from the device's metro) and as a `retransmit-only` badge on the shreds devices tab and in the subscribe flow, so a subscriber sees that a seat excludes leader shreds before funding it. Existing rows default to 0 (the bit was reserved and unset onchain, so no backfill is needed); the added payload column changes each metro's `attrs_hash`, so the first indexer run after deploy writes one new history row per metro. The public `/api/v1/edge/shreds/devices` contract is unchanged. Also fixes the shreds devices and metro-histories handlers returning a silently truncated 200 when the ClickHouse result stream fails mid-scan (missing `rows.Err()` check, pre-existing) (#2091)
- Publish serviceability feeds (Generalized Payments) to ClickHouse: new `dz_feeds_current` view (SKU catalog: feed → metro + joinable multicast groups), plus `dz_users_current.feed_pks` (JSON array of the EdgeSeat feeds a connected user consumed seats on) and `dz_access_passes_current.feed_seats` (per-feed seat billing lifecycle on EdgeSeat passes). Bumps the doublezero SDK to pick up the `Feed` account, `User.FeedPks`, and `AccessPass.FeedSeats` (#2068)
- Shared `utils/pkg/logger` helpers: transient-aware `logger.Error`/`logger.Warn` and consecutive-failure `logger.Escalator`; logging-level convention documented in CLAUDE.md (#696)
